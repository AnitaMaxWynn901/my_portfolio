Training YOLO for Cattle Behavior Detection

6 min read YOLOv8, YOLOv11, Roboflow, Python

This was my senior project — building a computer vision system that could watch CCTV footage of cows and classify their behavior in real time. The goal was to detect estrus (heat) automatically, which is important for livestock management.

Why Behavior Recognition?

Estrus detection in cattle is traditionally done manually, which requires constant observation and is easy to miss. Mounting behavior is a key indicator. If a model can detect mounting reliably from video, it can alert farmers automatically and save a lot of time.

Dataset Construction

The first challenge was data. We recorded footage from real farm CCTV cameras, then manually annotated each frame using Roboflow. We labeled four behavior classes:

  • Standing
  • Lying
  • Grazing
  • Mounting

Dataset quality matters more than quantity. We spent a lot of time making sure labels were consistent — a blurry frame with a wrong label is worse than no frame at all.

Model Training

We trained both YOLOv8 and YOLOv11 to compare performance. YOLOv11 gave better results on our dataset, especially for detecting the mounting class which had fewer examples.

yolo train model=yolov11n.pt data=cattle.yaml epochs=50 imgsz=640

Key things I learned about training:

  • Always check your class distribution — imbalanced data will hurt your minority class badly
  • Use augmentation (flip, rotate, brightness) but don't overdo it
  • Validate on real farm footage, not just your training split

Evaluation on Real Footage

The hardest part was getting the model to work on actual farm CCTV. The cameras were low resolution and had different angles than our training data. We had to fine-tune with a small set of real-farm-specific images to bridge that gap.

What I'd Do Differently

If I did this again, I'd collect data from multiple farms and multiple camera angles from the start. A model trained on one farm's footage generalizes poorly to another farm's lighting and angle. Also, tracking behavior over time (not just per-frame classification) would make the system much more useful.

Smart Retail Analytics: People Counting, Face Recognition & Heat Maps

7 min read YOLO, OpenCV, Face Recognition, NumPy

This was an internship project at CAS Cogniser that combined several computer vision tasks into one system: counting people entering and leaving a store, matching faces against a customer database, and generating heat maps of where people spent the most time.

System Overview

The system had three main modules running in parallel on a video stream:

  • People counter — entry/exit tracking using line-crossing detection
  • Face recognizer — match detected faces against a stored database
  • Heat map generator — track movement positions and build a density map

People Counting with Line Crossing

I used YOLO to detect people in each frame, then tracked them across frames using their bounding box positions. When a tracked person crosses a virtual line in the frame, it counts as an entry or exit depending on direction.

The tricky part is handling occlusion — when two people overlap, the tracker can get confused. I used a simple centroid distance approach which worked well enough for the store's layout.

Face Recognition Pipeline

For face recognition, the pipeline was: detect face → align → extract embedding → compare to database. When a match is found within a distance threshold, the dashboard shows "matched" with the customer ID. Otherwise it shows "no data".

# Simplified face matching logic
embedding = get_embedding(face_crop)
distances = [cosine_distance(embedding, db_emb) for db_emb in database]
if min(distances) < THRESHOLD:
    return "matched", customer_ids[argmin(distances)]
return "no data", None

Heat Map Generation

For each frame, I recorded the center point of every detected person. After accumulating these over time, I used NumPy to build a 2D histogram of positions, then applied a Gaussian blur and overlaid it as a colored transparency on the store map. High-traffic areas appeared in red, low-traffic in blue.

Dashboard

Everything fed into a live web dashboard showing the video stream, real-time occupancy count, entry/exit log, matched face list, and the heat map. Building this in a single day was intense but satisfying.

Building a Voice-Controlled Ad Display System with Python & Flask

5 min read Python, Flask, SpeechRecognition

During my internship, I built a system where voice commands could control which advertisement was displayed on a screen in real time. The use case was a digital signage screen in a retail environment where staff could switch ads hands-free.

Core Challenge: Reliable Continuous Listening

The biggest problem with voice systems is reliability. Background noise, accents, and silence all cause issues. I used Python's SpeechRecognition library with Google's speech API, running in a background thread so it never blocked the main app.

import speech_recognition as sr

def listen_loop():
    r = sr.Recognizer()
    with sr.Microphone() as source:
        r.adjust_for_ambient_noise(source)
        while True:
            try:
                audio = r.listen(source, timeout=3)
                command = r.recognize_google(audio).lower()
                handle_command(command)
            except sr.WaitTimeoutError:
                pass
            except sr.UnknownValueError:
                pass

Command Mapping

I built a dynamic command map that read the video folder structure automatically. If you had folders named "food", "tech", and "sale", the system would recognize phrases like "show food" or "play tech" without any hardcoding.

Auto-Demo Fallback

If no command is given for 30 seconds, the system falls into demo mode and cycles through all available ads automatically. This was important for when the screen was unattended — it kept content playing rather than freezing on one ad.

Flask UI

A small Flask web app provided a browser-based control panel as a backup. Staff could click to switch ads if voice wasn't working. The Flask backend and the listener shared the same state via a thread-safe queue.

What I Learned

Threading in Python is trickier than it looks when you need shared state. Using a queue.Queue instead of shared variables was the key to making it stable. Also, pre-loading videos into memory rather than streaming from disk made switching instant instead of having a 1–2 second delay.

Human Action Recognition: A Modular Image Processing Pipeline

5 min read Python, MediaPipe, OpenCV, Image Processing

This was a team project for an image processing course. The goal was to recognize human actions from images using classical image processing techniques — no deep learning allowed. It forced us to really understand what's happening under the hood.

Pipeline Overview

The system was broken into four clean stages:

  • Preprocessing — resize, normalize, convert color spaces
  • Segmentation — separate the person from the background
  • Feature extraction — extract meaningful descriptors
  • Classification — assign an action label

Segmentation

We tried background subtraction first, but it broke badly with varied backgrounds. We switched to using MediaPipe's selfie segmentation to get a reliable person mask, which we then used to isolate the subject before processing.

Feature Extraction

With MediaPipe's pose landmarks, we extracted 33 keypoints per frame. From these we computed joint angles (e.g., elbow angle, knee angle) and relative distances between keypoints. These angles and ratios were much more robust to scale and position differences than raw pixel coordinates.

# Compute angle between three landmarks
def calc_angle(a, b, c):
    a, b, c = np.array(a), np.array(b), np.array(c)
    radians = np.arctan2(c[1]-b[1], c[0]-b[0]) - \
              np.arctan2(a[1]-b[1], a[0]-b[0])
    return np.abs(np.degrees(radians))

Classification

We used a simple rule-based classifier first (if knee angle > 160 and hip angle > 150 → "standing"), then moved to a KNN classifier trained on a labeled dataset of poses. KNN worked surprisingly well given the clean feature vector we'd built.

GUI App

We wrapped everything in a Python GUI app using Tkinter that let users load an image or enable the webcam, run the pipeline, and see the result with annotated landmarks drawn on the image. Making it interactive made the demo much more convincing.

LINE Bot Ordering System: Auth, Role Dashboards & Real-Time Orders

8 min read Node.js, Express, LINE LIFF, Supabase

My most complex project so far. The goal was to build a complete food ordering system entirely inside LINE — one of the most popular messaging apps in Thailand — for a sushi cafe. Users could browse the menu, place orders, and track status, all without leaving LINE.

Why LINE LIFF?

LINE Front-end Framework (LIFF) lets you embed a web app inside LINE's browser. This means you can build a full React or HTML interface that runs inside a LINE chat, with access to the user's LINE identity. It's perfect for a food ordering flow.

Authentication

LIFF provides a user token automatically when a LINE user opens the app. I verified this token on the backend using LINE's API to get the user's LINE ID, then looked them up in Supabase to determine their role. 

const profile = await liff.getProfile();
const lineUserId = profile.userId;
// Send to backend to get role
const res = await fetch('/api/auth', {
  method: 'POST',
  body: JSON.stringify({ lineUserId })
});

Three-Role System

The system had three roles stored in Supabase:

  • Customer — browse menu, place orders, view order history, redeem points
  • Shop Master — manage incoming orders, update order status, view daily summary
  • Admin — manage the menu, view all orders, manage users and points

Each role got a different dashboard UI, all served from the same Express backend but with role-based route guards.

Real-Time Order Updates

I used Supabase's real-time subscriptions to push order status updates to the shop dashboard without polling. When an order status changed in the database, the shop master's UI updated instantly.

Points System

Every order added points to the customer's account. Points could be redeemed for discounts on future orders. The tricky part was making this atomic — you don't want to add points if the order failed, or deduct points twice. Supabase's database functions (RPC) handled this cleanly.

Rich Menu

LINE's Rich Menu is the button grid that appears at the bottom of the chat. I configured different Rich Menus for different roles using the LINE Messaging API — customers got "Order", "History", "Points" buttons, while shop masters got "New Orders", "Today's Summary".

Weather Dashboard: Building My First React App with Live API Data

5 min read React, JavaScript, OpenWeatherMap API, Vercel

I built this project to get hands-on experience with React while connecting to a real API. The Weather Dashboard lets you search any city and see current conditions plus a 5-day forecast, deployed live on Vercel.

Component Structure

I kept the structure simple and clean:

  • App.jsx — main state management, API calls
  • SearchBar.jsx — controlled input with form submit
  • Forecast.jsx — 5-day forecast cards

Having the API logic all in App.jsx made it easy to pass data down as props and kept the child components focused on rendering.

Fetching from OpenWeatherMap

I used two endpoints — one for current weather and one for the 5-day forecast. Both needed an API key which I stored in a .env file using Vite's import.meta.env:

# .env
VITE_API_KEY=your_key_here

# In component
const API_KEY = import.meta.env.VITE_API_KEY;

Never hardcode API keys in your source code — even if the repo is private. Vercel lets you set environment variables in the project settings so the key stays secure in production.

Handling the Forecast Data

The forecast endpoint returns data every 3 hours for 5 days (40 entries total). To get one reading per day, I filtered to every 8th item — simple but effective for this use case.

const dailyForecasts = forecastData.list
  .filter((item, index) => index % 8 === 0)
  .slice(0, 5);

What I Learned About React

  • State and props flow — keep state as high as it needs to be, no higher
  • Async/await in event handlers — always handle loading and error states
  • Environment variables with Vite — prefix with VITE_ or they won't be exposed
  • Deploying to Vercel — just connect your GitHub repo and it auto-deploys on every push
